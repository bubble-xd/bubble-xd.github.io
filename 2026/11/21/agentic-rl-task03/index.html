Datawhale Agentic RL Lab Task03 学习笔记：Vision GRPO 与 GeoQA 实战

发表于2026-11-21|更新于2026-11-21|LLMAgentic RL
|总字数:2.4k|阅读时长:8分钟|浏览量:

这篇是 Datawhale Agentic RL Lab 组队学习的第三篇笔记，对应官方原文 Vision GRPO：GeoQA 图文推理实战。

这次我把图文输入接进 GRPO，用较小的配置跑了 20 步，并在同一批 GeoQA 测试题上比较 Base、Step 10 和 Step 20。除了弄清图像 token 怎么对齐，我还逐题检查了分数上涨到底来自哪里。

Vision GRPO

把整条 RL 链路推到多模态：模型先看一张几何图，再读取题目和四个选项，同一道题并发生成一组回答，最后靠可验证的选项奖励完成在线更新。使用的数据集是 GeoQA：中文几何问答数据集，每条样本都包含几何图片、题目、四个候选项、正确选项标签，以及数据集自带的解析等字段。共 5010 条，这次复现使用固定超参数，没有用原始 dev 集调参。

原始 split 数量 本章用途
train 3,503 全部用于训练
test 759 固定抽取 100 条用于评测
dev 748 本次实验不使用

Parquet（全称 Apache Parquet）是一种开源的列式存储（Columnar Storage）二进制文件格式，最初源自大数据生态，现在几乎是 Hugging Face 和大模型数据集的标配存储格式。
模型看到的只有图片、题目和选项，训练 reward 使用 label 生成正确选项（计算奖励分数），answer 中的原始解析不会作为监督文本送给模型，模型在训练时完全看不到 answer 里的标准解题过程 不去模仿 or 背诵
训练方式采用 LoRA, rank 32
Qwen/Qwen3.5-4B 有 40 亿参数，直接修改所有参数（全量微调）开销较大。LoRA（Low-Rank Adaptation，低秩自适应） 的思路是：

  • 冻结原模型庞大的权重矩阵 𝑊（比如大小是 𝑑 ×𝑘）不动；
  • 在旁边外挂两个很窄的小矩阵 𝐴（大小 𝑟 ×𝑘）和 𝐵（大小 𝑑 ×𝑟），只训练 𝐴 和 𝐵，用它们的乘积 𝐵 ×𝐴 来表达权重的更新量 Δ𝑊： ，其中系数由 LoRA 配置决定。
  • 这里的中间维度 𝑟 就叫 rank（秩）。rank 32 就是把 𝑟 设为 32。
    其实本质就是 A 矩阵降维，B 矩阵升维（从右往左计算）
    举个直观例子（假设原矩阵是 4096 ×4096）：
  • 原矩阵参数量：4096 ×4096 ≈1677 万
  • rank 32 的 LoRA 参数量：(32 ×4096) +(4096 ×32) ≈26 万（只有原矩阵的 ~1.56%）

Vision GRPO 和纯文本 GRPO 差异最大的地方：
在 train.py 中的 build_prompt_chunks 中先使用模型自己的 chat template 格式化消息，然后 image 内容放入占位符

渲染后的 prompt 会沿 <|image_pad|> 拆成三个 chunk：EncodedTextChunk + ImageChunk + EncodedTextChunk
整体流程如下。同题采样数由 group-size 决定，教程配置是 8，本次是 4。

这里只有成功解析出最后一个 \boxed{A-D} 且与标签一致时 reward = 1，答错或格式不对（包括超长截断没输出选项）reward = 0。整体强化学习流程和纯文本 GRPO 基本一致，主要差异在于多模态输入与对齐处理：除了把图片合成白底并编码成 ImageChunk 塞进 prompt 外，还必须用 image_processor 算出视觉 token 数并校验本地与远端 input_tokens 一致，这样构造 Datum 时才能用 0 精确占位整个图文 prompt 区间，让策略梯度只作用于模型生成的文本 completion。
然后开始把图文题目和模型回答拼成一条 Datum，同时告诉训练框架哪里只是上下文，哪里才真正计算梯度更新

因为大模型是自回归预测下一个 token（Next-Token Prediction）：输入第 𝑖 个位置，预测的是第 𝑖 +1 个位置的 token。举个例子：假设图文 prompt 总长是 10（含文本 + 图片视觉 token），模型生成的回答 sample.tokens 是 [t0, t1, t2, t3]（长 4）：

  • model_input 放入：完整 prompt（10） + sample.tokens[:-1]（[t0, t1, t2]，3）= 总长 13
  • observation_length = 10 - 1 = 9
  • target_tokens 放入：9 个 0 + 完整 sample.tokens（4）= 总长 13
    把它们上下对齐一下，就能看懂为什么要 -1：
下标位置 0 ~ 8 (共 9 个) 9 (prompt 最后一个) 10 11 12
model_input prompt 前 9 个 token prompt 第 10 个 token t0 t1 t2
target_tokens 0（不计算） t0 t1 t2 t3
logprobs 0.0 lp(t0) lp(t1) lp(t2) lp(t3)
advantages 0.0 A A A A
可以看到：
  1. prompt 最后一个 token 负责预测回答的第一个字 t0 ，所以 target_tokens 从下标 9（也就是 prompt_length - 1）开始接上 t0；
  2. 最后一个字 t3 后面已经没有要预测的内容了，所以 model_input 只需要输入到 t2（即 sample.tokens[:-1]），最终两边总长度刚好都是 13

踩坑记录：如果直接按原教程设 --batch-size 8 --group-size 8，1 个 step 最多会生成 64 条图文 Datum（每条都带 1 张图片），我在当前 PyTRIO 环境下遇到远端 Trainer 拒收并报错 InputRejected: batch exceeds image count limit。调小到 4×4 后顺利跑通，每步最多 16 张图。若想保留每题的采样数，可以先减小每步的题目数。

评测 Base 和 checkpoint

为什么训练时已有 reward，还要单独做评测？

  1. Base：未经本次 RL 训练的原始模型（这里是 Qwen/Qwen3.5-4B），用来建立Baseline。
  2. Checkpoint：训练途中或结束时保存的权重快照。在 train.py 中每次保存会生成两种路径，评测只用第一种：
    • sampler_weights（trio://.../sampler_weights/...-sampler）：仅含推理所需权重，专门拿来做推理和评测；
    • training_state（trio://.../training_state/...-state）：还包含优化器状态，专门用于断点续训。
  3. 为什么不能只看训练日志里的 reward 曲线？
    • 训练时每个 step 拿的是不同的训练题（难度有波动），且采样开了随机性（temperature=1.0）；
    • 评测必须把 Base 和 Checkpoint 放到同一批未参与训练的测试题上，其实就是控制变量法。

实验结果与个人理解

本次为了规避单批图片数上限，采用 4×4 配置（batch-size=4, group-size=4）跑了 20 steps。在固定 100 题测试集上，Base、Step 10 与 Step 20 的对比结果如下：

模型 Accuracy Format rate 条件准确率（格式正确时） 平均输出长度 评测耗时
Base (Qwen3.5-4B) 68.0% 70.0% 97.1% (68/70) 930.0 字 50.41s
Step 10 77.0% (+9.0 pp) 80.0% (+10.0 pp) 96.3% (77/80) 828.1 字 83.09s
Step 20 80.0% (+12.0 pp) 82.0% (+12.0 pp) 97.6% (80/82) 777.8 字 71.82s

我的实验观察

  1. 判对率的提升主要来自原先无法解析的题。 相同的 100 道题中，Base 有 68 道判对，Step 20 有 80 道。按题目 ID 对齐后发现，14 道题从无法解析变为判对，2 道题从判对变成无法解析；两次都能解析的 68 道题中，66 道都是对的，另外 2 道都是错的。平均输出从约 930 字缩短到 778 字。可以说模型更常在当前评测规则下给出可判分的正确答案，但还不能断定它更会做几何题，也不能只凭平均长度判断哪条回答被截断。
  2. 缩小每题的采样组也会改变训练。 同一题的采样如果拿到相同奖励，组内优势全为零。本次 20 个训练步中只有 13 步执行了有效更新。碰到图片预算时，减小每步题数和减小每题采样数并不等价：前者减少题目覆盖，后者减少同一题里获得不同奖励的机会。
  3. 这次耗时只作记录。 三次都是在远端运行，总耗时同时包含排队、初始化和生成等因素。没有做重复计时或拆分这些环节，不能用一次运行比较 Base 和 checkpoint 的推理速度。
