Datawhale Agentic RL Lab Task05 学习笔记：General OPD 实战与同步/异步对比

发表于2026-11-27|更新于2026-11-27|LLMAgentic RL
|总字数:1.7k|阅读时长:6分钟|浏览量:

这篇是 Datawhale Agentic RL Lab 组队学习的第五篇笔记，承接前序笔记 Task04｜General OPD 原理与实战，结合 datawhalechina/agentic-rl-lab 仓库中的 General OPD 实验手册 及同步/异步实现脚本（01-demo-sync.py、02-demo-async.py），对照 Task02｜损失函数与 GRPO 实战 梳理代码差异，并结合 10 步同步试跑的 SwanLab 监控曲线分析同步版局限与异步并发改造。

OPD 实战

读完 01-demo-sync.py，核心是看 Task04｜General OPD 原理与实战 里的 On-Policy Distillation 原理怎么落地成一个可运行的 PyTRIO 训练循环。它的整体骨架和 Task02｜损失函数与 GRPO 实战 高度复用，重点在于弄清监督信号切换成 Teacher logprob 后，数据流、采样角色和训练表现发生了哪些变化。

训练闭环与核心逻辑

整份脚本只把 DeepMath-103K 当作题目池（只取 question 字段，训练阶段不看标准答案），每一步按以下流程完成一次策略更新：

最关键的一段逻辑集中在内层轨迹处理：

  • 三个客户端各自的分工：training_client 持有 Student（默认 Qwen/Qwen3.5-4B）的可训练 LoRA 参数；student_sampler 由 training_client 导出，负责产出当前策略下的回答；teacher_client（默认 Qwen/Qwen3.8-27B）始终冻结，只对 Student 已经生成的完整轨迹调用 compute_logprobs。
  • Teacher 打分对齐：必须把 prompt_ids + completion_ids 拼成完整上下文再算 compute_logprobs，然后取 all_logprobs[len(prompt_ids):]，保证 Teacher 是在与 Student 完全一致的历史前缀下评价每一个生成 token。同时脚本严格校验切片长度一致且不含 None，这要求 Student 和 Teacher 必须共享兼容的 tokenizer。

与 GRPO 实战的关键差异

相比之前跑过的 GRPO 同步脚本，OPD 复用了一样的 Datum 右移掩码（len(prompt_ids) - 1）和 importance_sampling 更新接口，核心差别在三处：

对比维度 GRPO（Task02） General OPD（01-demo-sync.py）
监督信号来源 本地规则核对标准答案（0/1 Reward） 冻结 Teacher 对轨迹的逐 token logprob
Advantage 粒度 序列级：同一条回答所有 token 共用同一个标量优势 Token 级：每个 completion token 各自有独立的 （即 -beta * reverse_kl）
group_size 作用 必须大于 1 才能算组内相对优势，同组全对/全错会导致退化 无需组内归一化，即使 group_size=1 也能产生有效梯度

这一点在 build_opd_datum 里最明显：GRPO 往 padded_advantages 填的是 [sample.advantage] * len(tokens)（整条回复同涨同跌），而 OPD 填的是逐位列表 list(advantages)（同一条回复里，Teacher 赞同的 token 会被拉高，不赞同的 token 会被压低）。

同步版实验结果分析

本次使用同步版跑完 10 步试跑（Step 0–9，batch_size=4、group_size=4、max_tokens=512、学习率恒定 4e-5），SwanLab 曲线如下：

  • 全部回答触及长度上限：data/datums 稳定在 16（无空序列跳过），但 data/completion_tokens_mean 全程是一条贴在 512 的直线（completion_tokens_total 恒为 8192）。这说明在 DeepMath 题目上，10 步内几乎所有样本都在写完前被 max_tokens=512 截断，后续评测需要放宽生成长度是不是效果会好？
  • Reverse KL 整体下移但单步波动明显：opd/reverse_kl_mean 从 Step 0 的约 0.159 下降到后期 0.105–0.129 区间（Step 6 为 0.119），opd/reverse_kl_std 同步从约 0.74 收窄到 0.59–0.64（Step 6 为 0.5965）。曲线出现起伏主要是因为每步只抽 4 道不同的题目，题目难度差异会直接拉动 KL 均值，加上总步数只有 10 步，仍处在初期对齐阶段。
  • Loss 走势与 Token 统计：严格 on-policy 下 importance ratio 接近 1，因此 trainer/loss_mean（约 0.084–0.141）的形态基本跟着 opd/reverse_kl_mean 走；trainer/token_count（约 9200–10450）比恒定的 8192 多出的 1000–2200 个 token，正好对应每步 16 条样本里随题目变化的 prompt 长度。
  • 单步耗时波动大：串行等待叠加远端波动导致耗时不稳定。

同步版局限

  • 串行网络往返是主要耗时瓶颈：同步版外层按 batch_size 串行等待 Student 采样 .result()，内层又对每条 seq 串行等待 Teacher 打分 .result()。按本次 4 × 4 配置，每步要串行等 4 次采样加 16 次 Teacher 打分，放大 batch 后耗时会线性拉长。
  • 短截断限制推理完整度：在 max_tokens=512 下样本被全部截断，Teacher 只能对前半段未完成的推理过程给 KL 信号，难以覆盖到最终得出 \boxed{} 答案的收尾步骤。
  • KL 下降不代表正确率必然上升：opd/reverse_kl_mean 下降只说明 Student 的输出分布更接近 Teacher，实际数学解题准确率仍需用导出的 LoRA 权重单独验证。
  • On-policy 严格度受刷新间隔制约：sampler_refresh_steps=1 保证每步严格 on-policy，但每步都要同步一次采样权重；若为省开销调大该值，间隔内会退化为轻微 off-policy，依赖 importance_sampling 纠偏。

异步版（02-demo-async.py）的主要区别

异步版与同步版在算法上完全一致（同样的数据加载、Reverse KL 公式、Datum 右移和 importance_sampling 更新），核心改动全在并发调度上：

对比项 同步版（01-demo-sync.py） 异步版（02-demo-async.py）
Prompt 级采样 for row in batch 逐题 sample().result() asyncio.gather 并发提交整批 run_prompt_rollout
Teacher 逐轨迹打分 for seq in sequences 逐条 compute_logprobs().result() 单题内再用 asyncio.gather 并发执行 compute_logprobs_async
SDK 调用方式 同步阻塞接口（create_* / sample / forward_backward） 全套 *_async 异步接口，用 asyncio.run(main(...)) 驱动
远端更新排队 连续调用 forward_backward 与 optim_step 后 .result() 先 await *_async 拿到两个 future，再依次 await 等待完成

本质上，异步版通过外层多题并发 + 内层多条轨迹并发打分，把原本 batch_size + batch_size * group_size 次串行等待折叠成两段并发等待，同时补充了 student_lps 与 completion_ids 的长度一致性校验，适合在更大 batch_size 和 group_size 下压低单步耗时。
